# EZPZ File JTD: 企画書

**日本語** · [English](PLAN.en.md) · [한국어](PLAN.ko.md)

> 一太郎の `.jtd` ファイルを、だれでも、どの端末でも開いて、直して、別の形式に移せるようにする
> オープンソースプロジェクト。韓国の rhwp が hwp で実現したことを、jtd で行う。

作成 2026-10-01 · 状態: v0.3。読み込みエンジン、一太郎風エディタ、`.jtd` への再保存

---

## 1. なぜやるのか

- jtd は日本の官公庁や学校にいまも多く残っているが、**一太郎は Windows 専用**。Mac・Linux・
  スマホ・ブラウザでは、事実上開く方法がない。
- 形式が公開されていないため、ほかのプログラムが読めない。その結果、jtd の文書は jtd のまま残り続ける。
- **形式を解き明かして公開すれば**、だれでも jtd を読むツールを作れるようになり、開かれた形式
  （docx・PDF・HTML）への移行が早まる。これがこのプロジェクトの本当の目的である。

## 2. 既存のものと、このプロジェクトの位置

| | できること | 限界 |
|---|---|---|
| 一太郎ビューア（公式） | 閲覧 | Windows 専用 |
| OpenOffice 一太郎フィルタ（2009） | 読み込み | Windows の DLL、更新停止 |
| OpenJTD / Tika-JTD（2026、Apache-2.0） | テキスト抽出、構造の RFC | 書式・表の見た目・編集はなし |
| ezpzfile.com JTD ビューア（TypeScript） | ブラウザで閲覧・Word 書き出し | サイトに組み込まれている |
| **EZPZ File JTD（このプロジェクト）** | **エンジン + 形式仕様書 + ビューア → エディタ** | - |

独自の手法: **「対になるファイル」分析。** 官公庁は同じ文書を jtd と Word の両方で公開することが多い。
Word 側の書式（文字サイズ・太字・揃え）はわかっているので、2 つのファイルを 1 文字ずつ突き合わせれば、
jtd の未知の数値の意味を機械的に割り出せる。一太郎がなくても形式を解ける方法である。

## 3. 初日（2026-10-01）の結果

- **新エンジン `ezpzjtd`**（Rust。外部ライブラリは文字コード変換と JSON 用の最小限のみ）: 公開されている
  jtd **95 件すべてが開ける**。1 ファイルあたり約 2 ms。
- **本文の文字: 対の Word ファイルと 97 % 一致**（残りは一部の表のセルを読む順番の違い。欠けた文字は事実上ない）。
- 表示できるもの: 段落、中央・右揃え、表（結合セル、列幅の比率）、縦罫線の有無、文字サイズ、太字、下線、
  文字色、ルビ、改ページ、文書情報（元の保存場所を含む）。
- 書き出し: テキスト、Markdown、HTML、JSON。WebAssembly（ブラウザ用）にもビルドできる。
- **既存の分析になかった新しい発見**（詳細は `docs/spec/JTD-FORMAT.md`）:
  1. `DocumentText` はひと続きの文章ではなく **256 バイトのブロック格納庫（SsmgV.01）**。大きな文書は
     本文が複数の断片（`QLSTV.01`）に分かれる。既存の分析はこの構造を扱っていないため、大きな文書の本文を
     正しく読めないことがある。
  2. 段落先頭のレコードは **（タグ、個数、値）のリスト**。3,638 件すべてが正確に一致。タグ `0x24` が
     **段落の揃え**であることを Word の対で確認。
  3. 文字属性番号の意味: **2 番 = 文字サイズ（1/100 mm 単位）**、1 番 = 太字、13 番 = 下線、15 番 = 色。
     Word の対 22,722 文字で確認。
  4. 罫線情報 `0x8F` の項目の文法（線あり 4 項目 / 線なし 2 項目）。罫線のない行を区別できるようになった。

### 同じ日の午後: jtd への再保存（v0.3）

- **本物の一太郎ビューアを審判にする。** 無料のビューアをクラウドの Linux 上で Wine と日本語環境で動かし、
  ファイルを開く・画面を撮る・テキストをコピーするところまで自動化した（`tools/taroview/`）。
  韓国語版 Windows（コードページ 949）ではビューアがすべてのファイルで落ちるため、この方法を選んだ。
- 読み込み結果をビューアの表示と比較: **見える文字の 99.9 % が一致、94 件中 87 件が完全一致**。
  この比較で「行の途中にある段落先頭レコードは新しい段落ではない」ことを見つけて直した。
- **保存のしかた: 元のファイルを書き換える。** 変わった文字・段落・書式・揃え・改ページ・表の行だけを
  書き換え、わからない部分はそのまま残す。保存したファイルを読み直してエディタの内容と比べ、違っていれば
  保存しない。
- **重要な発見: `\x04JSRV_SegmentInformation`。** 格納庫ごとにある「ストリーム一覧 + サイズ」の表。
  サイズが 1 つでも合わないと、ビューアは「ファイルを読み込めません」と拒否する。これを合わせたことで、
  サイズが変わる編集も開けるようになった。
- ランダム編集の保存成功率（公開 jtd 95 件 × 3 回）: 文字 96 %、書式を含めて 99 %、表・改ページを含めて
  90 %。残りは理由を示して保存を断る（罫線のセルをまたぐ行の結合、ルビの中での改行、罫線内の新しい表）。
- エディタ: Ctrl+S で jtd に保存。PDF は画面どおりの見た目で、検索・コピーできる文字層つき。

## 5. 運営の原則

- **ezpzfile.com とは分ける**: 別のリポジトリで開発する。サイトに組み込むのはエンジンが十分に育ってから、
  WASM パッケージを 1 つ取り込む形に限る。
- **サンプルはリポジトリに入れない**: アドレスの一覧（`corpus/manifest.tsv`）だけを公開し、各自でダウンロードする。
- **確からしさを示す**: 形式仕様書のすべての項目に confirmed / strong / observed / candidate / unknown を付ける。
- **わからないバイトは捨てない**: 後で jtd に保存し直すために必要になる。
- **先行研究を尊重する**: OpenJTD・Tika-JTD の RFC を出典として明記し、こちらで新しくわかったことは
  先方にも共有できる形でまとめる。
- ライセンス: **MIT または Apache-2.0**（利用者が選ぶ）。rhwp（MIT）、OpenJTD（Apache-2.0）の両方と組み合わせられる。

## 7. リスク

- **法的**: 互換性のためのファイル形式の分析は一般に認められる方向だが、国や利用規約によって異なる。一太郎の
  プログラムそのものは分解せず、**ファイルだけを見て分析**している。法的助言ではない。
- **市場**: jtd は減っていく形式である。そのため「エディタとしての人気」より「開く・移すツール」としての価値が先にくる。
- **完成度**: 元とまったく同じ見た目を再現するには時間がかかる。段階ごとに「どこまでできるか」を画面で正直に示す。
